### Fresh sweep (git diff cbefb22..lane-h, excluding kitty-specs)

Probes ran `nextAnnouncement` over update sequences. The screen applies it pairwise in `willUpdate`, and the live region is keyed by seq, so these are the texts the screen speaks.

- **S-1 (sev2, introduced by the unchanged-rescan fix).** "No changes" is decided pairwise, so it is only right when the host clears `rescanning` in the same update that delivers the new report. Nothing in the contract requires that. A host that sets `report` after an await and clears `rescanning` in a `finally` produces two updates, and gets a contradictory pair in either order:
  - Report first, then flag: `Rescanning` → `Rescanned: 3 findings, last scan 1 minute ago` → `Rescan complete: no changes`. The last line is false.
  - Flag first, then report: `Rescanning` → `Rescan complete: no changes` → `Rescanned: …`.

  The same pairwise rule says "no changes" when a rescan ends on an *older* `scannedAt` (P10), and that report is shown. It also swallows a copy result that lands in the same update as the end of a rescan (P5).

  Only the single-update ordering is tested (header.test:229, :257). Remedy: decide "unchanged" against the report at the rising edge. Either keep a rescan baseline (`scannedAt`/`count` captured when `rescanning` rises) in the screen and pass it in `AnnounceInput`, or suppress the completion line when a report line was already spoken since the edge. For flag-first ordering, either state in the contract that the host clears `rescanning` together with the new report, or defer the completion line. Pin both orders with screen tests.
- **S-2 (sev2, introduced by the F-3 fix).** F-3 now says "Rescanning" in the error and not-found states, but nothing replaces it when that rescan ends in the same state. Probe: error(x) → error(x)+rescanning → error(x) gives `["Rescanning", null]`, and not-found gives the same. The live region then keeps "Rescanning" standing indefinitely: the stale text the tracer ruling forbids. (Before round 2 these states said nothing at all, so this is new.) A rescan that leaves error for ready announces correctly (P11). Remedy: on the falling edge in error/not-found with the state unchanged, announce `RESCAN_UNCHANGED_ANNOUNCEMENT`, or re-announce the state line, and add the test.
- **S-3 (sev1, the tokenizer-based no-copy scan).** It has three blind spots:
  - (a) `isCopy` passes any literal that has no whitespace and starts lower-case. Planted `'severity'`, `'rescanning…'` and `'no-changes'` all PASS. One-word lower-case copy is a known false-negative class, the cost of letting data-attribute values through. Document it in the test comment, or allow-list the known token values instead.
  - (b) Text in a tagged template that is not `html` (`svg`, `String.raw`, a custom tag) is skipped by both scans. A planted ``String.raw`Severity ${x}` `` PASSES. Treat any non-`css` tag like `html` for text nodes, or push its text.
  - (c) The tokenizer does not recognise regex literals. A planted `/'/` desynchronises it: the real copy literal after it is then read as code, and the junk between the quotes is reported instead. It failed loudly here because the junk held a space, but it can also report junk, which is a false positive.

  No regex literal holds a quote in the 8 files today. Remedy: a regex-literal skip (after `(`, `=`, `,`, `return`), or move the scan to the TypeScript AST (`ts.createSourceFile`), which removes (b) and (c).

  The scan also stops on an unterminated block comment: `indexOf` returns -1, `i` resets to 1, and the walk restarts. This is theoretical; the files compile.

  No false positive on the current files, since the gate is green.
