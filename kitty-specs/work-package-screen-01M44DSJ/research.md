## Decisions

### D-01 One public element, private parts
`sk-work-package-screen` is the only new public element. Header, facts and assignment, frontmatter, owned files, lane history, review, chains, subtasks, workspace, artifact links and the state panels are private fragments in `*-parts.ts` files next to it. Rejected: one pattern element per panel (eight new public surfaces with one consumer each; the charter asks for small stable interfaces and deep modules), and reusing `sk-work-package-board` pieces (a Work Package screen renders no board). Part files are the unit of write ownership between work packages (`plan.md`, "Shared files").

### D-02 Reuse of #4, by import, never by copy
The screen imports `defaults/`, `logic/` (`lookup`, `resolveStateBadge`, `resolveLaneLabel`, `resolveActivity`/`relativeTime`, `formatWholePercent` if the progress bar shows a figure), `view-state.ts`, `library-sheets.ts`, `progress-sheet.ts`, `visually-hidden.ts`, `overflow-region.ts`, `story-support/shell-frame.ts` and the shell's `flush` option. It also imports `STALE_BADGE` (the "stale" word and tone), `LANE_COUNT_TEXT` ("N Work Packages"), `SUBTASK_PROGRESS_TEXT` (the subtask bar label) and the `StateBadge`/`BadgeTone` types: no second home for any of them. New vocabulary goes in NEW files in `defaults/` (D-07), re-exported from `defaults/index.ts`. Event detail types are imported with `import type` from the dispatching elements of #4 (`SkSelectWorkPackageDetail`, `SkOpenMissionDetail`): one declaration, no copy. Rejected: moving the types into a shared `events.ts` (edits accepted code of #4 for a style gain; revisit at a later mission).

### D-03 View states: `status` plus `detailStatus`, declared on the screen
`WpScreenStatus = ViewState | 'not-found' | 'nothing-selected'` and `DetailStatus = 'loading' | 'ready' | 'error' | 'not-found'` are declared in `sk-work-package-screen.ts` (not in `view-state.ts`, which stays the charter's four). Unknown `status` collapses to `empty` (same normaliser style as `normaliseViewState`: a local `normaliseWpStatus` using the `ViewState` normaliser for the four and an allow-list for the two). `detailStatus` defaults to `'ready'` (a host that passes `detail` and no status gets the detail); an absent `detail` with `detailStatus` `ready` means "the host omitted the detail" (FR-004 degradation), distinct from `loading`. The manifest declares both properties (FR-028, FR-032).
