## Decisions

### D-01 Element decomposition: two screens, three pattern elements, the rest private fragments

| Unit | Kind | Why |
|---|---|---|
| `sk-missions-screen` | screen (`@screen`, `status`) | the Missions screen |
| `sk-pipeline-screen` | screen (`@screen`, `status`) | the Pipeline screen |
| `sk-filter-toggle-group` | pattern element | the one place that holds the native `<button aria-pressed>` exception (D-15); a small generic interface (options, value) that a later Work Packages screen can reuse |
| `sk-phase-bar` | pattern element | the heart of the FUTURE CONSTRAINT (C-007); testable alone with 3 and 7 unknown phases; the one place that may need the paint exception (D-17) |
| `sk-work-package-board` | pattern element | lane-group prop, placement algorithm, scroll-region semantics, card rendering; testable with custom groups |
| mission row, work-package card, inspector, page headers, state panels | private fragments (render functions in a `*-parts.ts` beside the owner) | one consumer each; every extra element costs at least 4 stories, 4 baselines, a manifest entry and tests (README "Add an element"); their behaviour is covered through the owner's stories and tests |

Rejected: a `sk-mission-row` element (only the Missions screen renders rows; its logic is a pure function, `buildRowView`, unit-tested without stories); a `sk-wp-card` element (cards exist only inside the board); a `sk-pipeline-inspector` element (a composition of library elements, one consumer); one monolithic element per screen (the 3-and-7-phase test and the custom-lane-group test need the pieces alone, and the exception scopes in D-15 need small files).

### D-02 Where files live, and one shared story helper

Elements stay under `src/elements/<tag>/` with `@screen` in the class JSDoc for the two screens, as `sk-mission-shell` does (the `src/screens/` path would also work for the manifest gate but the ESLint `unbound-method` override and every precedent point at `src/elements/`). Registration only in `src/index.ts`. New non-element source: `src/contract/` (generated types, generated fixtures, bulk fixtures, type aliases), `src/defaults/` (vocabulary: every contract value and its English copy), `src/logic/` (algorithms: placement, lane summary, search, relative time, row view), `src/library-sheets.ts` (adopted library stylesheets), `src/story-support/shell-frame.ts` (story-only helper that wraps a screen in `sk-mission-shell`, outside the manifest globs and not exported from `index.ts`). Stories and tests may import `src/story-support/`; elements may not: the mechanism is a `no-restricted-imports` block in `eslint.config.mjs` (files `packages/*/src/elements/**/*.ts`, ignoring `*.stories.ts` and `fixtures.ts`, pattern `**/story-support/**`), written in IC-03b and proven there once by a temporary violating import (`gates.md`, eslint row).

Rejected: putting the helper in a `*.stories.ts` (Storybook turns every export of a stories file into a story); a helper under `src/elements/` (enters the manifest scan).

### D-03 Event ownership: the dispatching element is the only emitter; library events stop at the boundary

Exactly one dispatch site per event (the README rule "`this.dispatchEvent(new CustomEvent('<literal>', ...))`" is kept):

| Event | Dispatched by | Detail |
|---|---|---|
| `sk-open-mission` (EV-1) | `sk-missions-screen` | `{ missionId, slug }` |
| `sk-filter-change` (EV-2) | `sk-filter-toggle-group` (bubbles and composed through the screen) | `{ filter }` |
| `sk-search` (EV-3) | `sk-missions-screen` | `{ query }` (trimmed text) |
| `sk-load-more` (EV-4) | `sk-missions-screen` | `{ cursor }` |
| `sk-select-work-package` (EV-5) | `sk-work-package-board` (bubbles and composed through the screen) | `{ missionId, wpId }` |
| `sk-view-artifacts` (EV-6) | `sk-pipeline-screen` | `{ missionId }` |
| `sk-open-missions` (EV-7) | `sk-pipeline-screen` | `{}` |

The two screens declare the child-dispatched events in their class JSDoc `@fires` (FR-026: every emitted event of a screen is in the manifest; `check-manifest.mjs` accepts a `@fires` with no local dispatch). Library `sk-action-row-activate` events are stopped (`stopPropagation`) at the element that translates them, as `sk-mission-shell` and `sk-shell-tree` do; nothing but the seven `sk-*` names crosses a screen boundary. All events `bubbles: true, composed: true`, none cancelable. Event names and payloads are the operator-accepted defaults of the issue and brief (B); the payload `filter` is the filter id (`all`, `active`, `planned`, `done`, `stale`, `discarded`).

Rejected: pattern elements emitting neutral events that the screen re-dispatches (two dispatch sites and two sets of tests per intent, for no gain: the payload each pattern element can build is already complete, because `sk-work-package-board` takes `missionId` as a property the way `sk-shell-nav-item` takes `itemId`); non-bubbling internal events (the charter says intents bubble and are composed).

### D-04 Property surface of the screens (data in as properties, typed from the contract)

`sk-missions-screen`: `status`, `project: Project | null`, `branch: string` (host value; FR-001), `missions: MissionOverviewView[]`, `pageInfo: PageInfo | null`, `now: string | null` (ISO instant), `filter: string` (default `all`), `query: string` (default empty), `loadingMore: boolean`, `laneGroups: LaneGroup[]` (default from `defaults/lanes.ts`), `labels: LabelHooks | null`, `errorMessage: string`. `sk-pipeline-screen`: `status`, `mission: MissionDetailView | null`, `laneGroups`, `labels`, `missionsHref: string` (default `#/missions`), `errorMessage`. `missionsHref`, both `errorMessage` properties and the `label` property of the phase bar, the board and the filter group are not named by the spec: amendment proposal P-7. Exact tables in `contracts/`. A screen takes the contract object as one property plus host extras as separate properties, never a flattened re-shaping, so SC-008 (a host passes only contract-shaped data, branch, `now`, optional `stale` and actor) holds by construction.

Rejected: splitting `MissionDetail` into `phases`, `workPackages`, `progress`, ... properties (a host would re-shape the contract); a `MissionDetail` plus `branch` prop for the Pipeline (the contract already carries `targetBranch`, which is what FR-012 and FR-020 show: no host prop).

### D-05 Widened view types (FR-014, C-007)

`src/contract/types.ts` aliases the generated schemas and widens exactly three things, all additive supertypes of the contract types so a contract object is assignable without a cast: `PhaseView = Omit<MissionPhase, 'name'> & { name: string }`; `WorkPackageView = Omit<WorkPackageSummary, 'statusLane'> & { statusLane: string | null; actor?: string }`; `MissionDetailView = Omit<MissionDetail, 'phases' | 'workPackages'> & { phases: PhaseView[]; workPackages: WorkPackageView[] }`; and `MissionOverviewView = MissionOverview & { stale?: boolean }`. One more type exists only for fixtures: `MissionOverviewPageView = Omit<MissionOverviewPage, 'items'> & { items: MissionOverviewView[] }`, the `satisfies` target of the host-kind page fixtures (a `satisfies` against `MissionOverviewPage` rejects the host `stale`, TS2353); no element type uses it. `statusLaneCounts` stays the contract type and is consumed as `Readonly<Record<string, number>>`. Phase `status` stays the closed three-value union; an unknown status renders as pending (D-27). Host fields live INSIDE the object they describe (rejected: a `staleIds: string[]` side list and an `actors` map keyed by `wpId`: two structures to keep in step with the list, and the fixtures and the contract gate would need a second host-field channel).

### D-06 Label hooks and the defaults module (FR-006, FR-010, FR-014)

One optional hook object per screen: `LabelHooks { phase?(name): string | undefined; lane?(lane): string | undefined; state?(lane | null): StateBadge | undefined; time?(iso, now): string | undefined }`. Resolution is always `hook?.(x) ?? DEFAULT[x] ?? raw` with `Object.hasOwn` lookups (a phase named `constructor` must render as itself). Defaults are data, not code: `src/defaults/{lanes,phases,lifecycle}.ts` (API in `contracts/defaults.md`). Rendering code never branches on a phase name, a lane or a lifecycle value; it looks them up. Rejected: one hook per element property (boilerplate), a `switch` over phase names with a `default` (violates FR-014 and the new gate), locale-aware `Intl` formatting inside the screen (locale access is the "locale I/O" FR-010 excludes).

### D-07 Board: lane groups as a prop, one placement algorithm (FR-015, FR-016)

`LaneGroup = { id: string; label: string; lanes: string[] }`. Placement (data-model.md has the diagram): a work package goes into the FIRST group whose `lanes` includes its `statusLane`; a `null` lane goes into the first group with the "not started" badge; a lane no group holds goes into the first group with a state badge showing the raw lane value; input order is kept within a column (the service orders by `wpId` ascending as plain strings; the screen does not re-sort). A lane listed by two groups belongs to the first. The column count is the number of cards the column renders. The default five groups live in `defaults/lanes.ts` exactly as the operator decided (Planned: planned, blocked; In progress: claimed, in_progress; Review: for_review, in_review; Approved: approved; Done: done, canceled). Zero groups render the board's empty copy and keep every work package unplaced (an empty `laneGroups` array falls back to one synthetic group labelled by the board `label`, so nothing is dropped).

### D-08 Gate 1 `data-driven`: the design

Name `data-driven`; CI job id `data-driven`; command `pnpm lint:data-driven && pnpm test:data-driven` (same shape as `no-io`). Full design in `contracts/gates.md`. Summary: an ESLint config `eslint.data-driven.config.mjs` with `linterOptions.noInlineConfig: true` (otherwise one `eslint-disable` comment silences the gate, reproduced) and 31 `no-restricted-syntax` entries (one per selector alternative), selectors S1 to S12, over these shapes: string `Literal` and exact `TemplateElement` of the 14 `WORDS` (five phase names, nine lanes), the four status words `pending`, `complete`, `draft`, `discarded`, markup text next to a tag or an expression, attribute values, underscored lane substrings, CSS attribute selectors, identifier keys and type members, enum members, any-object property reads of a lane or phase word, counts-object reads, `phases[<n>]`, `.at/.slice/.splice/.with(<n>)`, array destructuring of `phases`, `phases.length` against a literal of 2 or more, regex literals, destructured lane words, and hard-coded counts in CSS (`repeat(5, ...)`, `nth-child(5)`); the exact table is `contracts/gates.md`. Scope `packages/*/src/**/*.ts` minus an allow-list (`src/defaults/**`, `src/contract/**`, `*.stories.ts`, `fixtures.ts`, `*.fixtures.ts`, `src/story-support/**`; tests live outside `src`); the vocabulary values the gate checks (14 `WORDS` plus the four status words; `active` is deliberately not gated) live only in `src/defaults/`, and elements consume them through typed lookups, so the legitimate collisions (`SubtaskProgress.done`, `MissionPhase.status` `in_progress`, lifecycle `planned` and `done`) never occur in scanned code; no planned type has a field named like a lane or a phase (`RowView.blockedBadge`); a self-test that cannot pass vacuously (36 positive fixtures (one per selector alternative) with expected selector ids, a count guard, negative fixtures, allow-list cases with a positive control, a disable-comment fixture); a plant (a lane literal in element source); behavioural tests (3 and 7 unknown phases with a layout assertion, custom lane groups, a fully foreign vocabulary).

Rejected: an AST script on the TypeScript compiler API (a second parser and more code than the selectors need); a grep gate (matches comments and strings inside JSDoc, cannot see object-key or index shapes); a type-level approach (the vocabularies are `string` at the element boundary by D-05, so types cannot forbid a literal); scanning only the two screens (the phase bar, the board, cards, inspector and lane summary are where a literal would hide).

### D-09 Contract consumption: vendor the pinned files byte for byte

Vendored at `contracts/spec-kitty/mission-status/**` and `contracts/spec-kitty/_shared/**` (the same relative layout as upstream, so `../../_shared/...` refs resolve), with `contracts/spec-kitty/PIN.json`. `.gitattributes` gets `contracts/spec-kitty/** text eol=lf linguist-vendored` (without `eol=lf` an autocrlf checkout changes the hashes; without `-diff` a re-pin stays a reviewable diff). CI is offline and hermetic; a re-pin is one reviewable PR.

| Option | Verdict |
|---|---|
| Vendor + `PIN.json` + hash gate | chosen: hermetic, reviewable, zero network in any gate, 98 files and about 420 KB |
| Fetch at gate time | rejected: every gate and proof leg gains a network dependency and a failure mode that is not ours; a moving remote can silently change what is tested |
| Git submodule | rejected: the repo is private and the contract repo is public; submodules need a second checkout step in the install composite action, and CI's frozen install cannot see them |
| npm package | rejected: spec-kitty publishes no contract package (inference from the repo layout: Gradle and Python tooling only) |
| Vendor only `mission-status/` | rejected: the `$ref` into `_shared` would dangle (verified) |

### D-10 Type generation (FR-026, C-002)

`openapi-typescript@7.13.0` over the vendored `openapi.yaml`, run by `pnpm contract:generate` (`scripts/contract/generate.mjs`, programmatic API, so the output is deterministic and carries a header: tool and version, the pin sha, the contract version, the command, no absolute path) into `packages/mission-ui/src/contract/types.generated.ts`, committed. The `contract` gate regenerates in memory and byte-compares (freshness). `src/contract/types.ts` (hand-written) re-exports named aliases and the widened view types (D-05). The generated file is ignored by ESLint by exact path (exception E-05: the tool's `unknown & unknown` output trips `@typescript-eslint/no-redundant-type-constituents`; freshness is the gate's job) and is covered by typecheck, no-io, hygiene, Stylelint (no CSS) and the data-driven allow-list. Dependencies: `openapi-typescript@7.13.0`, `@apidevtools/json-schema-ref-parser@16.0.3`, `ajv-formats@3.0.1` as exact-pinned ROOT devDependencies (scripts only, nothing ships); `ajv` 8.20.0 and `yaml` 2.9.1 exist. The lockfile changes once, in IC-01, by an online install; CI keeps `--frozen-lockfile`, and the proof legs' `pnpm install --offline --frozen-lockfile` works because the store is warm after that install (gate-proof local mode already documents the requirement).

Rejected: hand-writing the types (drifts silently); `@redocly/openapi-core` (not needed); committing types without a freshness check (a stale file is exactly the failure the pin exists to prevent); `quicktype`/JSON-schema-to-ts (the contract is OpenAPI 3.1 split across files, openapi-typescript is the tool that resolves it, verified).

### D-11 Fixtures: derived from the examples, extended by named overlays, generated, fresh-checked

A generator (`scripts/contract/generate.mjs`, same command) reads the vendored `examples/` (YAML via `yaml`), applies named overlay functions from `scripts/contract/overlays.mjs` (plain JS, pure, each documented: what state the examples lack and why it is needed) and writes `packages/mission-ui/src/contract/fixtures.generated.ts`: data only, `import type` only, every export ending `satisfies <view type>`, so `tsc` checks every fixture against the generated and widened types (this is the "typed" in "typed overlays") and plain Node can load it by type stripping (to be confirmed in S0, below). Each export carries a `// fixture: <name>` comment line. Large synthetic data (the 500-Mission page of NFR-006, the 40-row list) comes from self-contained pure functions in `src/contract/bulk.ts` (no value imports, so the gate can load and validate it too). Fixture inventory and the overlay each one needs are in `contract-pin.md`.

Overlays tally `statusLaneCounts`, `wpTotal` and `blockedCount` mechanically from the work packages they set and DECLARE every other derived value per fixture as a literal (`progress`, `lifecycleStatus`, `acceptedAt`, `nextAction`, the `implement` and `review` statuses); `weightedPercentage` is declared too, with the value the producer (`compute_weighted_progress` at the pin; weights in `contract-pin.md`) would compute for the fixture's counts. The gate (D-12, C5) recomputes everything the contract defines exactly, and that figure with the producer's weights held as one constant, with its own implementation, so no fixture contradicts the contract it claims to follow: this is what makes PL-01 resolvable (below). `contracts/contract-pin.md` lists every declared value. Every export ends `satisfies` the target named in the inventory (a contract type for valid documents, a view type for host and relaxed ones). Rejected: hand-written TS fixtures (not derived, not validated); fixtures as JSON plus a typed wrapper (needs a cast from JSON to the union types, and the cast is exactly where a wrong fixture would hide); a JSON-patch DSL for overlays (a second language for ten functions).

### D-12 Gate 2 `contract`: design

Name `contract`; CI job id `contract`; command `pnpm contract:check && pnpm test:contract`. Seven checks (full text in `contracts/gates.md`):

- C1 pin integrity: every `PIN.json` file hash equals the vendored bytes, the file set equals the directory's, `infoVersion` equals `info.version` of the vendored `openapi.yaml`, `changelogTopVersion` equals the newest `## <x.y.z>` heading of the vendored CHANGELOG, the sha is 40 hex.
- C2 generated types are fresh.
- C3 generated fixtures are fresh (regenerated in memory, byte-equal).
- C4 every fixture validates against the dereferenced pinned schema with ajv 2020 (closed shapes). Host-only fields (`stale` on a Mission overview, `actor` on a work package summary; every `actor` must be in `SYNTHETIC_ACTORS`) are stripped by a registry-declared path list before validating; the screens' types carry them separately (D-05). Fixtures deliberately outside the contract (PL-07's 3 and 7 phases, the unknown lane value) are in an explicit registry with a NAMED relaxation (`phases-open`, `lane-open`: a schema patch with declared JSON-pointer edits and an allowed-error-path pattern). ### D-21 Filter and search: algorithm, state ownership, events (FR-002, FR-003, FR-009)

State is held by the screen (properties `filter` and `query`, settable by the host: host-set values change the view and never emit; only user input emits). Algorithm (`src/logic/search.ts`, `defaults/lifecycle.ts`): a Mission is shown iff it matches the active filter AND the query. Active filter: the entry of `FILTERS` with that id (an unknown id behaves as the default entry, no event); predicates are `lifecycleStatus` equality for four filters, `stale === true` for Stale, always true for All (a draft appears only under All because no other filter matches `draft`; a stale and active Mission appears under both Active and Stale). Query: `needle = query.trim().toLowerCase()`; empty needle matches everything; otherwise `[friendlyName, slug, missionType ?? '', topology].some(field => field.toLowerCase().includes(needle))`: plain substring, no regular expression, no tokenising, so `a.b` or `(` is text. `sk-search` is emitted with the trimmed query when the trimmed query changes (a whitespace-only change is not a new query and emits nothing); `sk-filter-change` when a different filter is pressed. No debounce (a timer would also be flagged by NFR-005's spirit; 500 rows are cheap, D-23). Rejected: searching lifecycle words and badge words as the prototype's `data-search` attribute does (spec FR-002 names name, slug, type, topology); regular-expression search; debounce.

### D-22 Paging: Load more, busy, no infinite scroll (FR-008)

`pageInfo` property; the row renders as the last `li` iff `pageInfo.hasNextPage && pageInfo.nextPageCursor !== null`; activation emits `sk-load-more { cursor: pageInfo.nextPageCursor }`. `loadingMore: boolean` is owned by the host (the screen owns no load): while true the row's `sk-button` is `busy`, `aria-busy` is set on the row and a further activation emits nothing. The no-match panel renders the same row beneath it. Nothing loads by scrolling (no `IntersectionObserver`, no scroll listener). A `hasNextPage` true with a null cursor is a contract violation the screen treats as "no next page" (it cannot emit a meaningful cursor).

### D-23 NFR-006: 500 Missions in 200 ms

Rows are rendered once, keyed by `missionId` (`repeat`), each inside an `<li>`; the filter and query only toggle the `li`'s `hidden` property. Hiding the `li` (not the `sk-action-row`) matters: the library element sets `:host { display: block }`, which beats the UA `[hidden]` rule, so `hidden` on the custom element itself would not hide it (inference from the library CSS, to be confirmed in spike S3). A toggle is then 500 attribute writes, not 400 element constructions. The unit test acts on a 500-Mission page and measures `performance.now()` around the action and `await el.updateComplete`, asserting 200 ms or less (initial render is not measured). The timing is the budget; the proof that the hidden-`li` design is what is measured is structural and required in the same test: 500 Mission `li` before and after, the SAME `li` node references after the action (no re-creation), at least one and not all `li` hidden (a strict-subset filter or query), the toggle case pressing the real filter button and the search case typing into the real inner `input` of `sk-form-input` (the keystroke path of NFR-006), not assigning a property. A failing timing on a shared runner is investigated, not loosened. Rejected: re-rendering the filtered subset (constructs up to 500 shadow roots on "All"), virtual scrolling (spec forbids infinite scroll semantics and adds a scroll listener), a Web Worker (forbidden by no-io).

### D-28 Shell footer and inspector agree: one additive property

### D-34 Test strategy

Unit and interaction tests (Vitest browser mode, `page.viewport` first and reset after each test as the shell tests do): defaults and logic are pure functions tested directly (placement, lane summary, search, relative time, row view, label resolution); each element has behaviour tests (properties, a11y structure, every event with its payload, no-event assertions: pressing the pressed filter, a whitespace-only query change, activating Load more while busy, host-set properties, library events not leaking); screens have state tests (four view states, header kept, no controls in loading and error), NFR-006, 3 and 7 phases, custom groups, a foreign vocabulary, footer and inspector agreement, Tab-walks per tier, 200% root font. Estimated 225 tests (an estimate; the count is not a requirement): about 130 browser-mode tests (the `unit-tests` gate), about 55 vitest node tests (`test:data-driven`: 36 positive, negative, allow-list, disable-comment and count-guard cases) and about 40 node:test cases (`test:contract`: the negative cases, guards and tooling tests of `contracts/gates.md`).

**Test quality rules (binding; stated in every WP brief, checked by every reviewer).** The charter wants every event and its payload asserted; these rules make a test fail when the behaviour is reverted instead of passing vacuously:

1. Every no-event test carries a positive control in the same test: the same listener, on the same target, receives an event when a sibling action that does emit is performed (a listener on the wrong target or a misspelt event name cannot make "emits nothing" pass).
2. Every emit test asserts exactly one event (`events.length` equal to 1, so a library `click` bubbling beside the screen's own would show), `bubbles` and `composed` true, `cancelable` false, and the detail with deep equality (`toEqual`, not `toMatchObject`).
3. Counts are asserted with equality (3 and 7 phases, five columns, 22 fixtures, 118 stories against 118 baselines), never "at least". Every loop over fixtures, stories or items asserts that the loop ran the expected N times.
4. Every changed behaviour has a revert check: the WP report lists, per test file, one deliberate revert of the behaviour (a temporary local edit in the work-package worktree, never committed), the failing test name it produced, and the restore; the reviewer re-runs two of them.
5. The C-009 terminology check is a node test with a known-positive sample so it can fail (`scripts/terminology.test.mjs`, owned by IC-09; run by `pnpm test:scripts`, which is wired into the `hygiene` gate under ruling P-9, exception E-06); it scans `packages/*/src` source text and this mission's reader-facing guide `quickstart.md` (a docs line is how the word survived a source-only scan) for the word "feature" (case-insensitive, whole word; the spec, plan and decision records are not scanned because they quote the rule and the spec's own future-work prose) and its own test feeds a sample containing the word and requires a hit.
6. The 500-Mission test follows D-23 (structural assertions are the proof, the timing the budget).

### D-36 PR shape and wrap-up (operator standing rule, binding)

One pull request for the whole mission, opened only after: accept, dev-assist test cleanup, aggregate review squad, compaction of history into a few logically sliced commits, rebase onto `main`, a full gate re-run, and then the DRAFT pull request.
