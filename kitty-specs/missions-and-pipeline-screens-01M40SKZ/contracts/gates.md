# Contract: the two new gates (`data-driven`, `contract`) and how every existing gate applies

Every gate is a CI job whose id is its gate id (`ci.yml`): a job with one `id: gate` step (no `if:`), a plant directory under `gates/plants/<id>/`, an entry in the `proof-leg` matrix written exactly like the `no-io` one (`{ gate: <id>, timeout: <minutes>, image: '' }`; the `image` key is mandatory because the job runs `container: ${{ matrix.image }}` and `SK_VISUAL_IMAGE: ${{ matrix.image }}`), a need in `all`, a row in the README gates table and a changelog line.

**What is mechanically enforced and what is not.**

| Enforced by | What |
|---|---|
| `node scripts/gate-proof.mjs coverage` (`coverageProblems` in `scripts/gate-proof/lib.mjs`) and hygiene `checkWorkflow` (`scripts/hygiene/rules.mjs`) | gate job ids = `matrix.gate` list = `gates/plants/*` directories (= fragment set in the final job); `all.needs` is exactly the gate jobs plus `proof-leg` and `proof`; each gate's plants declare one distinct `ciCommand` equal to the `run:` of the one `id: gate` step (no `if:`, keys limited to `id`, `name`, `run`, `env`); digest-pinned images; action pins |
| the proof record schema (`validateRecord` in `scripts/gate-proof/lib.mjs`) | every fragment's `gate` is in the schema's `gate` enum (see "Third coupling" below) |
| reviewer checklist ONLY, not mechanically enforced | the `timeout` and `image` values of a matrix include (coverage checks the gate list, not the include entries), the README gates-table row, the CHANGELOG lines |

No script reads README or CHANGELOG (`grep README|CHANGELOG scripts/` has no hit); a stale row cannot fail a gate, so each work package's reviewer checks both by hand and the work package report lists them.

**Third coupling: the proof record schema and its test.** `validateRecord` compiles `kitty-specs/storybook-scaffold-01M3SYDA/contracts/gate-proof-record.schema.json`, whose `gates.items.properties.gate.enum` lists exactly the ten existing gate ids, and `scripts/gate-proof/gate-proof.test.mjs` hard-codes `const GATES = [ten ids]` and `assert.equal(rec.gates.length, 10)` while running `assemble()` against the real repository root (so `coverageCheck` there reads the real `ci.yml`, plant directories and fragments). Adding a gate job without these edits turns `Gate: proof` red. Therefore:

- IC-01 adds `contract` to the schema enum and to `GATES` in the test (11 ids, `rec.gates.length` 11); IC-02 adds `data-driven` (12 ids, 12). `minItems` stays 10 (a lower bound).
- **Recorded exception X-1 (not a library gap, so no G row):** this edits a file of an earlier, accepted mission (`storybook-scaffold-01M3SYDA`). It is an additive enum value with no other change. The PR description lists it with scope (one enum, two values), rationale (the schema is the proof record's contract for the gate set) and sunset (none; every future gate repeats it); it needs the operator's approval like any exception.
- Exit checks for IC-01 and IC-02, in addition to the single-gate leg: `node --test scripts/gate-proof/` passes; `node scripts/gate-proof.mjs coverage` prints no problem; an `assemble` dry run over fragments produced by `node scripts/gate-proof.mjs local --only <id>` for every gate passes the schema. `scripts/gate-proof/gate-proof.test.mjs` and `scripts/hygiene/hygiene.test.mjs` are run by `pnpm test:scripts` (wired into the `hygiene` gate by IC-01, ruling P-9); `no-io` additionally gets `noInlineConfig` and a plant in IC-02 (ruling P-10, exception E-07).

**The two new gates have no CI run to scale from, so their numbers (proof-leg 8 and 6, job 5 and 5) are ESTIMATES, stated as such, and are replaced by measured ones inside the work package that adds the gate.** The cost drivers are known but not measured: one `pnpm contract:check` is a dereference of the 98-file vendored set, an `openapi-typescript` run, and Ajv over 22 fixtures; `pnpm test:contract` repeats the real check about 40 times on mutated temporary copies (the cases share one dereference and compiled validator through a module-level cache keyed by the sha256 of the vendored schema bytes, and only the cases that mutate a schema file bypass it); the proof leg runs the clean command once and the three plants, two of which stop at `contract:check`, so it executes about 4 checks and 2 test suites plus its own set-up. The `data-driven` gate is smaller (one ESLint pass over the sources and a vitest file of about 55 tests). The derivation rule, applied by IC-01 for `contract` and by IC-02 for `data-driven` from a local run in the clean worktree: let C be the wall-clock of the gate command, L the wall-clock of `node scripts/gate-proof.mjs local --only <gate>`, and S = 120 s the fixed CI set-up allowance (checkout, install, cache restore; the visual job's fixed part is 70 s). Job timeout = ceil((2 x C + S) / 60) minutes, floor 5; proof-leg timeout = ceil((2 x L + S) / 60) minutes, floor 6, where the factor 2 stands for a CI runner slower than the local machine. The WP report records C, L and the two results; if either differs from the estimate in the table, the work package writes the derived value into its `ci.yml` entry and this table (IC-01 and IC-02 own those entries). The first pull-request run's durations are then compared with these under the 70 percent rule below.

Only the `proof (visual)` timeout must rise substantially; the others rise by two minutes for headroom. The sequence is not circular: IC-01 records the baseline (D-37) as the local wall-clock of `pnpm test`, `pnpm build-storybook` and one `pnpm visual` run (58 PNGs) beside the run ids above; IC-09 writes the visual and unit-tests timeouts into `ci.yml` from this table, before the pull request exists. The `contract` and `data-driven` timeouts are written by IC-01 and IC-02 from measurements on a partial tree, so they are PROVISIONAL: IC-09 re-records C and L for both gates on the integrated tree (all five elements, 60 stories, the final fixtures) and confirms that the written timeouts still satisfy the rule, raising them in `ci.yml` and in this table if not. The PR description states "timeouts derived from runs 36880654992 and 36882394060 scaled by 590/290". When the first pull-request run completes, the orchestrator posts its measured durations as a PR comment. If a gate timed out or used more than 70 percent of its timeout, ONE explicit fixup commit that changes only the timeouts (in `.github/workflows/ci.yml`, with the matching figures in this table) is the single allowed commit after the draft pull request opens (the operator is told; history is not rewritten again). Sharding the visual job remains the fallback and is an operator decision (it changes `ciCommand` and the plant).

## Gate `data-driven`

Purpose: no element hard-codes the five phase names, the nine status lanes or the four other contract status words listed below, so the later dynamic pipeline needs no screen change (C-007, FR-013 to FR-015). It fails when any scanned source contains one of those values in one of the shapes below. It does NOT cover every lifecycle value (see Vocabulary).

**Mechanism.** `eslint.data-driven.config.mjs` (the same pattern as `eslint.no-io.config.mjs`, its own named job) with `no-restricted-syntax` selectors; rule messages begin `data-driven: S<id>` so a test can tell which selector fired. `linterOptions: { noInlineConfig: true }` is part of the config: with a config shaped like the earlier draft (no `linterOptions`), a line `// eslint-disable-next-line no-restricted-syntax` or a `/* eslint-disable */` block above a violating literal silenced the gate completely (reproduced with ESLint 9.39.5); with the option both directives are ignored (ESLint adds a severity 1 "has no effect" notice with a null rule id and the severity 2 data-driven error stays). Not a script on the TypeScript compiler API and not grep (D-08). The same `noInlineConfig` line would close the same hole in `eslint.no-io.config.mjs`, which lacks it today; that is an edit of an accepted gate and is proposed as P-10, not done here.

**Scope.** Command `eslint -c eslint.data-driven.config.mjs packages/*/src`. Config `files: ['**/*.ts']`; `ignores` is the allow-list, nothing else: `**/src/defaults/**`, `**/src/contract/**`, `**/*.stories.ts`, `**/fixtures.ts`, `**/*.fixtures.ts`, `**/src/story-support/**`. Tests live in `packages/*/test/`, outside the scanned directory. Everything else under `packages/*/src` is scanned: every element, `view-state.ts`, `shell-types.ts`, `src/logic/**`, `src/library-sheets.ts`. The complete selector set below, run against the 12 files of `packages/mission-ui/src` that remain after the allow-list today, reports 0 problems (verified with the repository's ESLint 9.39.5 and typescript-eslint 8.71.0 in a scratch configuration), so no existing source needs a change.

**The one producer constant (rule e).** The contract text carries no lane weights, but its producer does: `check.mjs` declares `PRODUCER_LANE_WEIGHTS = { planned: 0, claimed: 0.05, in_progress: 0.3, for_review: 0.6, in_review: 0.7, approved: 0.8, done: 1, blocked: 0, canceled: 0 }` with a comment citing `src/specify_cli/status/progress.py`, symbol `DEFAULT_LANE_WEIGHTS` and `compute_weighted_progress`, at spec-kitty commit `9f41e48fe0e8b00cd040690598e90c37d82ea4a2` (verified by fetching the file at that commit at plan time; the formula and the declared fixture values are in `contract-pin.md`). This is the only place in the repository where a value of the producer is copied instead of read from the vendored contract; it is copied because the screens show this figure and a declared value that the producer could never emit is a fixture that is not a contract document (P-8), which a range check cannot catch. The rule is about weights and the tally rule of the contract, not about reachability: fixtures with a null or unknown-lane work package (`detailBadges`, `detailUnknownLane`) follow the contract's tally rule (such a work package is not in `wpTotal`), so the producer, which would count it in its denominator, would not emit their `W`; `detailUnknownLane` is declared a deliberate non-producible document (its `lane-open` relaxation), and `detailBadges` carries the same property through its null-lane work package. A re-pin re-verifies it: `contract:verify-remote` additionally fetches `src/specify_cli/status/progress.py` at the pinned sha, extracts the `DEFAULT_LANE_WEIGHTS` entries for the nine lanes, and fails when they differ from `PRODUCER_LANE_WEIGHTS` (the extraction is a pure function with a node test over a captured excerpt); a drift in the producer therefore surfaces as a failure of step 1 or step 7 of the re-pin procedure, with the instruction to update the constant and the declared values together. The contract gap (the contract names the symbol but not the weights) is raised on the existing upstream contract issue by the orchestrator, never by a mission.

Unknown-lane rule: the tally covers only the nine known lanes. **C6 username leg.** The hygiene path rules fire only for `/home/<name>`, `/Users/<name>` and Windows `Users` paths; a bare login in free text (an actor string, a title) would pass them. C6 therefore adds (1) `SYNTHETIC_ACTORS`, a constant array in `overlays.mjs`: the only values overlays may write into `actor`, and C4 fails on any other; and (2) a scan of every string VALUE of the generated fixtures, of the output of the `bulk.ts` generators and of the authored fixture and story files for the current OS username (`os.userInfo().username`, read when the gate runs, skipped when shorter than 4 characters), whole word, case-insensitive. Limits, stated in the README and in P-2: the scan can only detect the username of the machine or runner executing the gate, not another person's login; the vendored YAML is not scanned for the username (it is byte-identical to upstream by C1, and the contract prose contains common words such as `root`); a login that is neither in a path nor in the author's own account is outside what any gate here detects, and NFR-007's username leg is therefore covered by the path rules, the allow-list and this scan, not by a general detector.

**How these tests are exercised in CI.** The plant `ciCommand` is `A && B` (`pnpm contract:check && pnpm test:contract`): a planted run that breaks the check stops at A and never reaches B, so plants 1 and 2 do not exercise the tests.
