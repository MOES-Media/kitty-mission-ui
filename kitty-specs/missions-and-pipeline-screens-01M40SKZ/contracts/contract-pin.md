## Fixture inventory

Every contract document is built from a vendored example by a named overlay in `scripts/contract/overlays.mjs`. What an overlay computes and what it declares:

- Computed mechanically by the overlay's own tally function: `statusLaneCounts`, `wpTotal` and `blockedCount` from the work packages the overlay sets (null-lane and unknown-lane work packages are uncounted).
- DECLARED per fixture, as literals in the overlay and listed in the "Declared derived values" table below: `progress` (`weightedPercentage`, `donePercentage`, `doneCount`), `lifecycleStatus`, `acceptedAt`, `nextAction` and the `status` of the `implement` and `review` phases. `weightedPercentage` is declared too, but it is not free: it is the producer's lane-weighted readiness for the fixture's counts (weights below), and the gate (C5 rule e, `gates.md`) recomputes it independently with the same weights, as it does every other derived value. An overlay never computes any declared value, so a mistake in the overlay and one in the gate cannot hide each other. An overlay never inherits the base example's `progress`, `lifecycleStatus` or phase statuses by accident: every fixture below that changes the work packages states all of them.

`Kind`: `valid` (validates as is), `host` (carries host-only fields `stale` or `actor`, stripped before validation), `relaxed` (named relaxation, reverted-must-fail proof). `satisfies` is the TypeScript target the export ends with (data-model.md view types): `valid` pages and details use the contract type, `host` and `relaxed` ones the view type, because `satisfies` rejects excess properties (a `stale` on a `MissionOverview` item is an error against `MissionOverviewPage`, which is why `MissionOverviewPageView` exists). The list of 22 exports is complete and frozen for the mission: a work package that needs another fixture files a change request to the orchestrator (plan.md, shared files).

### Producer lane weights (the source of `W`)

`weightedPercentage` is produced by `compute_weighted_progress` in spec-kitty `src/specify_cli/status/progress.py` at the pinned commit `9f41e48fe0e8b00cd040690598e90c37d82ea4a2` (the contract's `MissionProgress.yaml` names it as `x-source`). The formula is `sum(wp_weight x lane_weight[lane]) / sum(wp_weight) x 100` with `wp_weight` 1.0 for every work package, and `DEFAULT_LANE_WEIGHTS` at that commit is:

| Lane | planned | claimed | in_progress | for_review | in_review | approved | done | blocked | canceled |
|---|---|---|---|---|---|---|---|---|---|
| Weight | 0 | 0.05 | 0.3 | 0.6 | 0.7 | 0.8 | 1.0 | 0 | 0 |

(The same map also lists `genesis` and `uninitialized` at 0; neither is one of the contract's nine lanes.) A canceled work package is in the denominator at weight 0, so a Mission whose work packages are all done or canceled is below 100 (`detailAllComplete`: 3 done and 1 canceled give 75, equal to its `donePercentage`). Verified at plan time by fetching the file at the pin and recomputing: every `MissionDetail`, `MissionOverview` and `MissionOverviewPage` example of the pin that carries a progress object (the ten example files; the non-empty ones give 65, 80 and 0) reproduces its declared `weightedPercentage` within 0.00005 under this formula, so the gate rule is not stricter than the contract's own data.

### Declared derived values (work packages and every value the gate checks or the stories show)

Counts and `wpTotal` are the overlay's mechanical tally of the listed lanes. `detailBothInProgress`, `detailEarly` keep the example's values (verified consistent). The phase columns are for `implement` and `review`; `specify`, `plan` and `tasks` keep the base example's statuses unless stated. `W` is the declared `weightedPercentage`, recomputed for this plan from the producer's lane weights (previous section, "Producer lane weights") over the counts in the third column: `W` = sum(count x weight) / `wpTotal` x 100, four decimals. A work package with a null or unknown lane is uncounted and not in `wpTotal`, which is the contract's rule. The producer would count every work package in its denominator, so for `detailUnknownLane` and `detailBadges` (null-lane work package) the declared `W` follows the contract's tally rule, not the producer's arithmetic. `detailUnknownLane` is a deliberate non-producible document: its `lane-open` relaxation is exempt from the producer-equality argument of rule e in `gates.md`, and C5 still recomputes `W` from the declared counts and `wpTotal` (15 = 0.3 / 2 x 100) exactly as for every other fixture.

## Named relaxations (`scripts/contract/registry.mjs`)

| Name | Patch applied to a `structuredClone` of the dereferenced schema | Allowed strict-error paths |
|---|---|---|
| `phases-open` | in `MissionDetail`: `phases` loses `minItems` and `maxItems`; `MissionPhase.name` becomes `{ type: string, minLength: 1 }`. The name-conditioned `allOf` of `MissionPhase` is KEPT: with an unknown name both `if` conditions are false and add no error (verified with Ajv 2020 in review), while a phase with a known name and a wrong `basis` still fails | `/phases` (length) and `/phases/<n>/name` only; NOT `/phases/<n>/basis` (a known-name defect would fail there or at `/phases/<n>`, both outside the pattern) |
| `lane-open` | in `WorkPackageSummary`: `statusLane` becomes `{ type: ['string', 'null'] }`. Tally rule: the nine known lanes only; a work package with a null or unknown lane is in no count and not in `wpTotal` (this text is in the registry entry, as is the C5 rule) | `/workPackages/<n>/statusLane` only |

`registry.mjs` clones the dereferenced schema per relaxation (`structuredClone`) and compiles the strict validator from the pristine copy, so a patch can never leak into the strict run. For every `relaxed` fixture the gate requires: valid under the relaxed schema; INVALID under the strict schema; every strict error's path matches the relaxation's allowed pattern. A registry entry that passes the strict schema is reported as stale. `registry.test.mjs` includes the case of a `phases-open` fixture with a known phase name and a wrong `basis`, which must fail the relaxed run (token `relaxation`).

## Re-pin, step by step

0. Initial vendoring (IC-01, once): after the vendoring commit, run `pnpm contract:verify-remote` and put its output in the PR description. A re-pin repeats it (step 7).
1. `pnpm contract:verify-remote` on the current pin (confirms the starting point is clean; the baseline gate run is green).
2. `pnpm contract:update --sha <new sha>`: it fetches that commit's `contracts/mission-status` and `contracts/_shared`, replaces the vendored copy (deleting files that disappeared), regenerates types and fixtures, rewrites `PIN.json` with the new sha, committer date, `retrievedAt`, `infoVersion`, `changelogTopVersion` and hashes, then runs `pnpm contract:check`.
3. Read the diff: vendored files first (what the contract changed), `types.generated.ts` second, `fixtures.generated.ts` third. The contract's own `CHANGELOG.md` entry is part of the vendored diff.
4. Run `pnpm typecheck`, `pnpm test` and the visual gate; a TypeScript or test failure where the screens depend on the changed shape is the signal of a breaking change.
5. Add a changelog line in `packages/mission-ui/CHANGELOG.md` ("Contract re-pinned to `<sha7>`, mission-status `<infoVersion>`").
6. Breaking change (a removed or retyped property, a new major `info.version`, the phases or status lanes going open): do not relax a closed shape and do not edit the vendored files. Stop; the fix to the screens is a spec amendment or a new mission. Contract gaps are raised on spec-kitty#5528 by the orchestrator, never by a mission.
7. The PR states the old and new sha and `infoVersion`; `contract:verify-remote` is run once more after the commit and its output goes in the PR description.
